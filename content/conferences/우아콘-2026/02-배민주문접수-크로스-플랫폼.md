## 핵심 내용

### 방법 1: 귀납적으로 시도하기

| 단계 | 하는 일 |
|---|---|
| 작업 분류 | 기존 MR을 쉬움, 보통, 어려움으로 나눔 |
| 시키기 | AI에게 작업을 맡기고, 결과를 사람이 보고 피드백 |
| 기록 | 피드백을 룰과 스킬에 계속 반영해 새 규칙을 쌓음 |

### 방법 2: 작업 단위와 역할 나누기

기획서 전체를 AI에게 한 번에 넘기면 빠지는 내용이 생깁니다. 그래서 작업 단위로 쪼개고, 단계마다 맡는 쪽을 정했습니다.

| 단계 | 담당 | 내용 |
|---|---|---|
| 작업 전달 | 사람 | 작업마다 해당 기획서와 피그마를 넘김 |
| 테크스펙 | AI | 작업별 테크스펙 작성 |
| 검토 | 사람 | 테크스펙 확인 |
| 구현 | AI | 검토를 통과한 테크스펙대로 구현 |

### 방법 3: 코드처럼 관리하기

규칙과 메모리 파일을 git으로 관리합니다. 개인 PC에만 남는 로컬 메모리 대신, 팀 전체가 같은 규칙을 보는 공통 메모리를 씁니다.

| 계기 | 규칙·메모리 파일 변경 |
|---|---|
| 정책·코드 변경 | 새 정책 규칙 추가, 코드 변경에 맞춰 규칙 수정 |
| LLM 버전 업그레이드 | 불필요해진 규칙 삭제 |
| AI 피드백 결과 | 공통 메모리에 반영 |

### 코드 리뷰 따라잡기

| 장치 | 역할 |
|---|---|
| CodeRabbit | 기본 리뷰 |
| 코드 리뷰 봇 | MR 단위 자동 리뷰 |
| E2E | Blink, WebKit에서 주문 접수, 주문 상세, 배달 완료 흐름 검증 |
| 구형 웹뷰 검증 | 최소 지원 버전(WebView 51)에서 Polyfill 누락과 CSS 깨짐이 없는지 테스트 |

### 정리

| 단계 | 담당 | 내용 |
|---|---|---|
| 기획·피그마 | | 입력 |
| 테크스펙 | AI | 기획과 피그마를 보고 작성 |
| 사람 검토 | 사람 | AI가 알 수 없는 영역 보완 |
| 구현 | AI | UI와 비즈니스 로직, 단위·통합 테스트 |

| 리뷰 | AI | 코드 리뷰 봇, CodeRabbit |

AI가 맡는 테크스펙, 구현, 검증, 리뷰는 모두 코드처럼 관리하는 룰·스킬·에이전트를 바탕으로 돌아갑니다. 사람 검토와 사람 승인에서 나온 피드백은 다시 룰·스킬·에이전트에 반영합니다.

### Windows 7 대응

Windows 7은 지원이 되지 않아 Delphi를 사용했습니다.

### Windows 트레이 팝업: `?` 대신 `#`

트레이 팝업에 주문 번호를 넘길 때 쿼리 문자열(`?`) 대신 해시(`#`)를 씁니다.

| 방식 | URL | 동작 |
|---|---|---|
| `?` 쿼리 | `{BASE_URL}/tray-popup?orderNo=...` | 넘길 때마다 페이지를 이동해 새 document를 만듦. 이전 document는 GC 전까지 렌더러 메모리에 남음 |
| `#` 해시 | `{BASE_URL}/tray-popup#orderNo=...` | `hashchange` 이벤트만 발생하고, document 1개를 유지한 채 내용만 교체 |

<details>
<summary>덧붙임: <code>#</code>만 바꾸면 새 document가 생기지 않는 이유</summary>

- URL에서 `#` 뒤(프래그먼트)는 문서 안의 위치를 가리키는 부분이라 서버로 보내지 않습니다. 브라우저는 프래그먼트만 바뀐 이동을 같은 문서 안의 이동으로 처리하고 페이지를 다시 불러오지 않습니다.
- `?` 뒤 쿼리 문자열은 리소스 주소의 일부입니다. 값이 바뀌면 다른 리소스로 보고 새로 요청해 document를 처음부터 만듭니다. 팝업이 뜰 때마다 이 과정이 반복되면 이전 document가 정리될 때까지 메모리가 쌓입니다.
- 해시 방식에서는 페이지가 `hashchange`를 직접 받아 화면을 바꿔야 합니다.

```ts
window.addEventListener("hashchange", () => {
  const orderNo = new URLSearchParams(location.hash.slice(1)).get("orderNo");
  render(orderNo);
});
```

- 프래그먼트만 바꿔도 방문 기록에는 항목이 하나씩 쌓입니다. 기록을 남기지 않으려면 `location.replace()`로 바꿉니다.
- 같은 문서 안에서 URL을 바꾸는 방법으로 `history.pushState()`도 있지만, 페이지 안의 스크립트에서만 부를 수 있습니다. 네이티브 쪽에서 웹뷰 URL을 바꿔 값을 넘기는 구조라면 해시가 더 간단합니다.

</details>

### 공통 인터페이스에 의존하기

웹뷰가 브릿지 인터페이스를 정의하고, React Native와 Delphi는 각자 이 인터페이스에 맞춰 구현합니다.

| 계층 | 내용 |
|---|---|
| 웹뷰 | 인터페이스 정의 |
| 브릿지 인터페이스 | TypeScript zod 스키마에서 Delphi 타입을 코드 생성 |
| React Native | zod 스키마를 가져와 구현 |
| Delphi | 생성된 타입을 가져와 구현 |

오디오 재생(`PLAY_AUDIO`)을 예로 들면 스키마는 한 곳에만 있고, 두 플랫폼은 같은 필드로 요청을 받습니다.

```ts
// @webview/bridge-interface
export const playAudioSchema = z.object({
  source: z.string(),
  isLooping: z.boolean().optional(),
});

// React Native
import { playAudioSchema } from '@webview/bridge-interface';

PLAY_AUDIO: async (data) => {
  const req = playAudioSchema.parse(data);
  await play(req.source, req.isLooping);
},
```

```pascal
// Delphi
uses BridgeInterface.Audio;

Req := TPlayAudioRequest.FromJSON(AData);
PlayAlarm(Req.Source, Req.IsLooping);
```

### macOS: 웹 콘텐츠 프로세스에 비공개 API 적용

WebKit 비공개 API 네 가지를 웹 콘텐츠 프로세스에 적용해 프로세스가 정지되는지 비교했습니다. `_setPageVisibilityBasedProcessSuppressionEnabled`를 적용했을 때만 정지가 없었습니다.

| 비공개 API | 정지 |
|---|---|
| `_setHiddenPageDOMTimerThrottlingEnabled` | 있음 |
| `_setHiddenPageDOMTimerThrottlingAutoIncreases` | 있음 |
| `_setPageVisibilityBasedProcessSuppressionEnabled` | 없음 |
| `_setWindowOcclusionDetectionEnabled` | 있음 |

### macOS: 공개 API로 해결

최종적으로는 공개 API로 해결했습니다. macOS 14부터 쓸 수 있는 `inactiveSchedulingPolicy`를 `WKInactiveSchedulingPolicyNone`으로 두면, 창이 보이지 않아도 웹 콘텐츠 프로세스를 정지하지 않습니다.

```objc
// 창이 보이지 않아도 웹 콘텐츠 프로세스를 정지하지 않음
if (@available(macOS 14.0, *)) {
  configuration.preferences.inactiveSchedulingPolicy =
    WKInactiveSchedulingPolicyNone;
}
```
