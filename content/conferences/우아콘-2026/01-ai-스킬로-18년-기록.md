## 핵심 내용

### ADR과 RFC 문서 구성

결정을 남기는 ADR과 의견을 구하는 RFC를 정해진 형식으로 씁니다.

**ADR (Architecture Decision Record, 아키텍처 결정 기록)**

| 구성 | 쓰는 내용 |
|---|---|
| `#` 제목 | 결정을 한 문장 명령형으로 |
| `## Status` | 제안, 승인, 기각 같은 결정 상태 |
| `## Context` | 결정이 필요한 배경과 제약 |
| `## Decision` | 확정한 결정을 단정형으로 |
| `## Consequences` | 좋아지는 점과 감수할 점 |
| `## Alternatives` | 검토한 대안과 고르지 않은 이유 |

**RFC (Request for Comments, 의견 요청 문서)**

| 구성 | 쓰는 내용 |
|---|---|
| `#` 제목 | 내용을 파악할 수 있는 제목 |
| `## 요약` | 제안 내용을 짧게 |
| `## 주요 문의 및 논의 사항` | 리뷰어에게 묻고 싶은 점. 질문마다 리뷰어가 의견을, 작성자가 답변과 반영 여부를 적음 |
| `## 과제 설명` | 배경, 목표, 해결 방안, 고려한 대안 |
| `## 수행 일정/계획` | 일정과 단계 |
| `## 부록` | 참고 자료 |

### 자주 남긴 검수 의견

| 항목 | 의견 |
|---|---|
| 독자와 목적 | 도입부에 배경, 주제, 대상 독자, 읽고 얻을 것 |
| 근거 | 주장의 이유와 근거(수치, 사례 등) |
| 제목과 본문 | 결론 먼저, 제목만 읽어도 주제를 알 수 있게 |
| 사실 확인 | 수치·인용 출처 표기, 고유 명사 확인 |
| 용어 일관성 | 같은 개념은 같은 용어로, 약어는 처음 나올 때 풀어 씀 |

### 문서 검수 스킬 예

검수 스킬은 문서를 여섯 갈래로 나눠 봅니다.

| 구분 | 점검 규칙 |
|---|---|
| 표기 | 같은 개념에 표기가 둘 이상이면 하나로 통일 |
| | 약어는 처음 나올 때 풀어 씀 |
| | 외래어는 외래어 표기법을 따름 |
| | 제품명, 서비스명은 공식 표기 그대로 |
| | 코드, 명령어, 파일명은 인라인 코드로 |
| | 숫자와 단위 표기 방식을 문서 안에서 통일 |
| 문장 | 한 문장에는 한 가지 내용만 |
| | 주어와 서술어 호응 확인 |
| | 번역 투 표현(~에 대해, ~을 통해) 순화 |
| | 지시어 대신 대상 이름 |
| | 피동 표현은 능동으로 |
| | 습관적인 접속사 줄이기 |
| | 같은 뜻 반복(중복 표현) 정리 |
| 문단 | 한 문단이 다섯 문장을 넘고 주제가 둘이면 지적 |
| | 30자 이하 문장이 한 문단에 셋 이상 이어지면 지적 |
| | 문단 첫 문장에 핵심 |
| | 앞 문단과 연결이 끊기면 지적 |
| | 한 문단에 예시가 연달아 나오면 하나만 |
| 구조 | 도입부에서 배경, 주제, 대상 독자, 읽고 얻을 것을 알 수 있게 |
| | 결론 먼저, 제목만 읽어도 주제를 알 수 있게 |
| | 소제목은 내용을 요약하는 말로 |
| | 목록 항목은 같은 형식으로 |
| | 표와 그림이 나오기 전에 설명 문장 추가 |
| 사실 | 수치, 인용, 고유 명사는 저자 확인 |
| | 출처 없는 인용 확인 |
| | 버전, 날짜는 원문과 대조 |
| | 추측을 사실처럼 쓴 문장 지적 |
| AI 티 | 과장 수식어(혁신적인, 획기적인) 지적 |
| | '~하는 것이 중요합니다' 같은 빈말 지적 |
| | 대구, 셋 나열 습관 지적 |
| | 문단 끝 요약 문장 반복 지적 |

### AI 티 나는 문체

AI 티를 문장 구조와 표현 두 갈래로 나눕니다.

- 문장 구조: 대조형, 순서 예고형, 그럴듯한 이유, 분열문, 단문 나열
- 표현: 추상 표현, 부풀린 평가, 문장 부호, '이, 그, 해당' 같은 지시어

| 유형 | 예문 |
|---|---|
| 대조형 | 이 도구는 단순히 로그를 모으는 도구가 아니라 장애 원인을 찾는 도구입니다. |
| 분열문 | 배포할 때 특히 유의할 점은 환경 변수 설정입니다. |
| 단문 나열 | TDD를 처음 적용했습니다. 테스트부터 짜는 게 어색했습니다. 속도도 느렸습니다. |
| 추상 표현 | 리팩터링은 과거의 나와 마주하는 일입니다. 낡은 코드를 손에 쥐고, 더 나은 구조로 나아가는 입구에 서는 것입니다. |

자주 쓰는 단어나 어휘는 코드로 감지하기도 합니다.

### 초안 점검 스킬 공개본

검수 스킬 중 최소 품질 점검 부분이 Claude Code 플러그인으로 공개되어 있습니다. 저장소: [young-twc/techwriting-tools](https://github.com/young-twc/techwriting-tools)

<details>
<summary>techwriting-min-check 요약</summary>

외부 공개 전에 작성자가 초안을 스스로 점검하는 스킬입니다. 글이 최소선을 넘었는지만 보고, 글의 완성도나 설득력, 문체 취향은 판정하지 않습니다.

**설치와 실행**

```text
/plugin marketplace add young-twc/techwriting-tools
/plugin install techwriting-check@techwriting-tools
/techwriting-check:techwriting-min-check <파일 경로, Google Docs 링크, 본문>
```

.md, .txt, .docx 파일, 붙여넣은 본문, Google Docs 링크를 받습니다. 결과는 채팅에 나오고 원본 옆에 `<원본 이름>_점검.md`로도 저장됩니다.

**점검 항목 18개**

| 구분 | 항목 |
|---|---|
| 1부: 구조와 틀 | 문서 목적, 대상 독자, 제목 명확성, 문서 구조 |
| 2부: 표현과 세부 | 민감 정보, 용어 약어 풀이, 용어 일관성, 번역 투, 겹말, 형식 일관성, 코드 표현 형식, 링크 무결성, 맞춤법 및 외래어 표기, 출처 표기, 저작권, 비문, 인증/시크릿 정보 노출, 미완성 흔적 잔존 |

**판정**

- 항목마다 통과 또는 보완 필요로 판정하고, 걸린 항목은 등급을 매깁니다.
- P0(필수 수정): 목적·독자를 알 수 없음, 제목 없음, 민감 정보나 인증 정보 노출, 출처 없는 인용·통계·이미지, 오탈자, 작성 중 흔적. 하나라도 있으면 통과하지 못합니다.
- P1(권장 수정): 독자 이해를 방해하는 항목. 고치지 않아도 통과합니다.
- P2(선택 수정): 이해에는 문제없지만 다듬으면 좋은 항목.
- 판정이 애매하면 통과로 봅니다. 본문만 받아 링크나 저작권을 확인할 수 없으면 확인 불가로 따로 표시합니다.
